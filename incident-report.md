# Incident Report: Suspicious Authentication Followed by Privilege Escalation

## Incident Summary

Microsoft Sentinel generated a high-severity incident after detecting repeated failed authentication attempts followed by a successful logon and subsequent addition of the same account to the local Administrators group.

The incident was generated by the custom analytics rule:

`Suspicious Authentication Followed by Privilege Escalation`

The activity was generated intentionally in a controlled lab environment for Blue Team detection engineering and incident investigation practice.

---

## Affected Asset

### Host

`win-blue-team-lab`

### Account

`soclab-user`

The incident was enriched with the affected Windows host through Sentinel Host entity mapping.

---

## Detection Source

The detection was based on Windows Security Events collected from the monitored endpoint through Azure Monitor Agent and Microsoft Sentinel.

Relevant events included:

- `4625` — failed logon;
- `4624` — successful logon;
- `4732` — member added to a security-enabled local group;
- `4720` — user account created, used as investigation context;
- `4672` — special privileges assigned to a new logon, used as additional investigation context.

The final detection did not require Event ID `4720`, because account creation may occur outside the analytics rule lookup period.

---

## Observed Activity

The controlled sequence consisted of:

```text id="tbp7na"
Failed Logon
Failed Logon
Failed Logon
Successful Logon
Added to Administrators
```

The test account generated multiple failed authentication attempts and was then successfully authenticated.

After the successful authentication, the same account was added to the local Windows `Administrators` group.

---

## SID Correlation

A key part of the investigation was verifying that the account which successfully authenticated was the same account later granted local administrative privileges.

The relevant fields were:

```text id="oe0mci"
4624 -> TargetUserSid
4732 -> MemberSid
```

The final detection collected both SID values and compared them using:

```kql id="dz61nj"
set_intersect(SuccessfulLogonSIDs, AdminMemberSIDs)
```

The detection required:

```kql id="pl0ef6"
array_length(MatchingSID) > 0
```

This confirmed that the SID from the successful authentication matched the SID later added to the local Administrators group.

---

## Temporal Correlation

The analytics rule also required the events to occur in the expected chronological order:

```text id="4qm0zm"
LastFailed < SuccessTime < PrivilegeTime
```

This reduced the risk that unrelated authentication and privilege-change events on the same endpoint would satisfy the detection.

---

## Detection Logic

The final detection used the following KQL:

```kql id="0mm98j"
SecurityEvent
| extend UserName = case(
    EventID in (4624, 4625), extract(@"([^\\]+)$", 1, Account),
    ""
)
| where
    (EventID == 4625 and UserName == "soclab-user")
    or (EventID == 4624 and UserName == "soclab-user")
    or (EventID == 4732 and TargetAccount has "Administrators")
| summarize
    FailedLogons = countif(EventID == 4625),
    SuccessfulLogons = countif(EventID == 4624),
    AdminGroupChanges = countif(EventID == 4732),
    FirstFailed = minif(TimeGenerated, EventID == 4625),
    LastFailed = maxif(TimeGenerated, EventID == 4625),
    SuccessTime = maxif(TimeGenerated, EventID == 4624),
    PrivilegeTime = maxif(TimeGenerated, EventID == 4732),
    SuccessfulLogonSIDs = make_set_if(
        TargetUserSid,
        EventID == 4624
            and isnotempty(TargetUserSid)
            and TargetUserSid != "S-1-0-0"
    ),
    AdminMemberSIDs = make_set_if(
        MemberSid,
        EventID == 4732
            and isnotempty(MemberSid)
    )
    by Computer
| extend MatchingSID = set_intersect(
    SuccessfulLogonSIDs,
    AdminMemberSIDs
)
| where FailedLogons >= 3
| where SuccessfulLogons >= 1
| where AdminGroupChanges >= 1
| where array_length(MatchingSID) > 0
| where LastFailed < SuccessTime
| where SuccessTime < PrivilegeTime
| project
    Computer,
    FailedLogons,
    SuccessfulLogons,
    AdminGroupChanges,
    FirstFailed,
    LastFailed,
    SuccessTime,
    PrivilegeTime,
    MatchingSID
```

## Automated Incident Response

A Sentinel automation rule named:

`Identity-Privilege-Escalation`

was configured to run when the incident was created.

The automation rule:

- changed the incident severity to `High`;
- added the tag `Identity-Privilege-Escalation`;
- created an analyst investigation task.

The task instructed the analyst to review failed and successful logons, validate the account SID, confirm the Administrators group modification, review related Windows Security Events, and determine whether containment was required.

No destructive containment action was automated.

## Investigation Findings

The investigation confirmed that:

- multiple failed authentication attempts occurred for `soclab-user`;
- the same account later authenticated successfully;
- the successful authentication contained a valid account SID;
- Event ID `4732` recorded a member being added to the local Administrators group;
- the `MemberSid` from the group change matched the SID from the successful logon;
- the failed logons occurred before the successful logon;
- the privilege escalation occurred after the successful logon;
- Sentinel generated the expected High-severity incident;
- the affected Host entity appeared in the incident graph;
- the automation rule added the expected tag and investigation task.

---

## Analyst Assessment

The sequence of repeated failed authentication, successful account access, and subsequent privilege escalation would represent high-risk behavior in a production environment.

The SID correlation significantly improves confidence compared with host-only event correlation because it verifies that the successfully authenticated identity was the same identity granted administrative privileges.

However, additional context would still be required before declaring the activity malicious.

Relevant investigation context would include:

- source IP address;
- logon type;
- initiating workstation;
- account history;
- endpoint process activity;
- privileged activity after authentication;
- network activity;
- EDR telemetry;
- whether the Administrators-group change was approved.

## Recommended Response

For a similar incident in a production environment, an analyst should:

1. Review the failed authentication attempts and their source.
2. Confirm the successful logon and associated account SID.
3. Validate that the same SID was added to the Administrators group.
4. Identify the account that performed the group membership modification.
5. Review the logon type and originating workstation.
6. Investigate Event ID `4672` and other privileged activity.
7. Search the endpoint for suspicious process execution.
8. Review persistence mechanisms and lateral movement.
9. Determine whether the activity was authorized.
10. Escalate to containment if compromise is confirmed.

If malicious activity is confirmed:

- disable or reset the compromised account;
- remove unauthorized Administrators-group membership;
- terminate active unauthorized sessions;
- isolate the affected endpoint if required;
- rotate affected credentials;
- investigate related systems;
- preserve logs and forensic evidence;
- continue incident response and threat hunting.

---

## Detection Limitations

The lab detection intentionally focuses on demonstrating SID and temporal correlation.

In a production environment, additional tuning would be required.

Potential improvements include:

- removing the hardcoded `soclab-user`;
- grouping dynamically by account or SID;
- correlating source IP and workstation information;
- applying environment-specific authentication thresholds;
- excluding known service accounts and approved automation;
- correlating with identity-provider telemetry;
- incorporating EDR process and network telemetry;
- enriching alerts with account risk and endpoint context.

---

## Lessons Learned

This project demonstrated that combining authentication events with privilege-management events provides stronger detection logic than analyzing each event independently.

SID-based correlation ensured that the same Windows identity was involved in both the successful authentication and the privilege escalation.

Temporal validation further reduced false correlations by enforcing the expected order of activity.
